NUA Performance Comparison

ML NUA vs GFX NUA — Benchmark Results

SSA Spiller · February 2026

Benchmarking methodology

Implementations under test

  • ML NUA — eager backward dataflow (fixed-point). PR #156079
  • GFX NUA — on-demand Dijkstra + BFS. PR #178873

How we measured

  • Timing: /usr/bin/time -f "%e"; median of 5 (wall-clock s). Output to /dev/null.
  • Memory: /usr/bin/time -f "%M"; median of 3 (peak RSS KB → MB).

What we ran

  • ML: llc -run-pass=amdgpu-next-use -amdgpu-next-use-dump-distance
  • GFX: llc -run-pass=amdgpu-next-use-analysis -amdgpu-next-use-analysis-dump-distance
  • Tests: 17 LIT tests (gfx1200, Debug); synthetic acyclic_*.mir & withloops_*.mir (gfx1200, Debug).
  • Stress test: bigSSA.mir — Blender Cycles GPU kernel (236 MB, 83K BBs, 1.9M instrs). gfx1030, Release-with-asserts.

Both sides use dump flag so analysis fully runs (fair comparison).

Bottom line

ML NUA is faster and uses less memory.

  • 1.00× – 1.09× faster on 17 LIT tests
  • Up to 12.7× faster on scaling synthetic tests
  • ~5–6.5× less peak memory at scale (80+ BBs)
  • 5.7× faster on Blender kernel (83K BBs) — GFX crashes

Debug builds, gfx1200. Both sides use dump flag. Median of 5 runs (timing) or 3 (memory).

LIT tests: Time gap vs. input size

Gap = GFX time − ML time (seconds). Larger gap ⇒ we are faster.

Observation: the trend is nearly flat — these LIT tests are too small to reveal the complexity difference. The gap does not clearly grow with input size.

Hypothesis: the gap should grow with input size due to quadratic vs. linear complexity. Does it?

Release-with-asserts builds, gfx1030, both with dump flag, output to /dev/null.

Why: in brief

  • ML NUA: fixed-point dataflow — one pass over the function; every query is an O(1) lookup into a precomputed snapshot. Linear in CFG size.
  • GFX NUA: on-demand Dijkstra + BFS per distance query; cost grows with CFG size and number of queries. Quadratic in CFG size.
  • ⚡ Faster — our fixed-point algorithm is linear; their Dijkstra is quadratic
  • 💾 Less memory — we store only per-register deltas; they build full path tables

Full design comparison and technical decision: see main NUA comparison presentation.

Two Algorithms, One Problem

ML NUA — Eager Dataflow

  • Classical backward dataflow (fixed-point iteration)
  • One upfront pass: O(iter × blocks × instrs)
  • Incremental events vector — stores only changed registers per instruction
  • Query: O(1) lookup into snapshot map
  • Integer arithmetic (int64_t), loop-aware tags
  • 2 pass dependencies (SlotIndexes, LoopInfo)

GFX NUA — Lazy On-Demand

  • On-demand Dijkstra + BFS per query
  • No upfront cost; computation deferred to query time
  • Per-query: O(V log V + E) Dijkstra + BFS
  • 7-level call hierarchy per distance request
  • Floating-point (double), 1000depth loop encoding
  • 5 pass dependencies (+LiveVars, LiveIntervals, DomTree)
Total complexity ML NUA GFX NUA
Precomputation O(iter × B × I) — one pass None (deferred to query time)
Per spill point (Q live regs) O(Q) O(Q × V × (V+E))
Total over S spill points O(iter·B·I) + S·O(Q) S · O(Q·V·(V+E))
B = basic blocks, I = instructions/block, Q = live registers (64–256 on AMDGPU), S = spill points, V = BBs in CFG, E = CFG edges. Per-query GFX cost: Dijkstra O(V log V) triggers ~V × BFS O(V+E) reachability checks.
